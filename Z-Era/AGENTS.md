# Token 效率协议

## 总纲
1. 证据优先：没有决定性证据，不改逻辑。
2. 一次到位：一次问全、一次读够、一次只验一个假设。
3. 结论优先：回复只承载"新增信息"，长度由信息量决定。

## A. 取证与诊断

| 症状 | 第一动作（不要跳过） |
|---|---|
| 视觉/UI 效果不对、看不到、位置尺寸异常 | 要用户截图存成文件并给路径，用 read_image 直接看；同时要目标的 RectTransform/布局数值 |
| 没日志、没声音、参数不对、行为不符预期 | 先只加"一次性完整状态打印"（对象、父链、关键字段、材质/资源、开关），拿到输出再动逻辑 |
| 报错/崩溃/编译失败 | 直接读原始报错全文，不要先猜、不要先重构 |
| 用户说"还是不行" | 先索要证据（完整日志行、参数值、截图），**不要立刻再发补丁** |

- A1 同一个 bug 连续两轮未解决 → 强制进入**诊断模式**：只加日志、只提问，不再提交任何"可能修复"。
- A2 **一次只验一个假设**：一轮改动只对应一个已确证的原因。禁止把多个投机修复叠在一次提交里——失败时无法归因，等于白跑一轮。
- A3 要"机器可读的事实"（日志行、数值、文件内容），不要"感受性描述"。
- A4 先查最可能且最便宜的三件事（尺寸/空引用/配置未保存/开关未启用），再谈复杂原因。

## B. 上下文经济
- B1 已经在上下文里的内容不重读；刚编辑过的文件不重读自证（语法交给编译器）。
- B2 读一次读够：能预判要用的多个片段就一次读完；否则 grep 精确定位 + 行窗口读。
- B3 **大输出隔离**：跨多文件扫描、大范围搜索、批量审查，交给 subagent/workflow 执行，只把结论带回主上下文。
- B4 场景/YAML/配置/日志只取必要字段，禁止整段 dump。
- B5 长任务用 todo 维护"已确证 / 已排除 / 待验证"，不要每轮重新推理同一件事。

## C. 工具使用上限
- C1 构建/编译一律 -v q（静默），绝不 -v n/detailed；需要确认"真的编译了"看产物是否存在与时间戳。
- C2 grep 用精确 pattern（符号名、GUID、字段名），结果加条数上限；
     禁止扫第三方目录与生成物（Packages、Library、node_modules、dist、build、obj/bin）。
- C3 长时间命令放后台跑，不要轮询；先做独立工作，最后统一收割。
- C4 临时脚本先小样本验证语法/接口，再全量跑（避免语法错误白跑一轮）。
- C5 优先用"一次交互回答多个问题"的检查（如一次性状态 dump），而不是多次往返。

## D. 提问与协作协议
- D1 便宜的问题早问：歧义会改变交付物时先问；能从既有惯例/代码推断的决定不要问。
- D2 一次问全，问题里写清"我需要什么格式的什么字段"。
- D3 提交改动时，同一条消息内附：预期现象、验证步骤、**需要回传的具体信息**（日志行/参数/截图），让下一轮能收敛而不是重开。
- D4 先声明关键假设再动手；假设成本低就直接做，错了再纠。

## E. 范围与改动纪律
- E1 只做被要求的改动；顺手的重构、加固、美化、兼容分支一律不做或先征询。
- E2 不做"投机性健壮性"：只处理已确证的问题，假设的边界等真出现再加。
- E3 一次 edit 只解决一个问题；改动保持最小可归因。
- E4 优先沿用工程既有惯例与抽象，不自创第二套实现。

## F. 回复纪律
- F1 结论/结果先行，解释在后。
- F2 不重述整体设计、不重复已给过的表格与代码、不复述用户刚说的话。
- F3 引用位置用文件链接+行号，不贴大段代码；确需 diff 只贴关键几行。
- F4 深入分析、长表格等用户主动追问时再展开。

## G. 技术栈专项：Unity / UI
- G1 agent 无法运行 Play 模式、看不到画面：视觉结论必须由人（截图）或日志确认，不要用补丁猜。
- G2 UI 溶解/遮罩类效果不生效，先查三件事：
     ① RectTransform 实际宽高（≤0 → Graphic 不生成网格，一个像素都不画）
     ② Graphic 材质的 Shader 名是否为目标 Shader
     ③ Canvas 的 additionalShaderChannels 是否含所需通道（如 TexCoord1）
- G3 暂停世界时动画/计时走未缩放时间；timeScale 收尾直接归位，不要"还原暂停前的存值"。
- G4 场景/预制体改动依赖磁盘状态：动手前先看目标文件 LastWriteTime，未保存的编辑器改动在盘上不存在。

## H. 例外与底线（这些地方不省）
- 破坏性/不可逆操作（删除、覆盖、迁移）、安全、数据一致性：先确认再执行，该花的 token 必须花。
- 正确性不为省 token 让步：宁可多读一遍关键文件，不凭记忆改代码。
- 用户明确要求完整性/全面性时，覆盖范围优先于简洁。
